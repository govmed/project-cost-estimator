# Deliverable #6 - Seed Data

The calculator works out of the box because of the data shipped here.
None of it is real - all rates and prices are explicitly marked illustrative
and meant as a sensible starting floor that the user customizes before any
real engagement.

## What's in this deliverable

```
seed/
  rate-cards/
    standard-2026-q1.json           # 1,953 entries, 46 roles x 5 levels x 9 geos
  cloud-pricing/
    aws-us-east-1.json              # 115 SKUs across 10 categories
    azure-eastus.json               #  98 SKUs across 10 categories

src/types/
  cloud-pricing.ts                  # TypeScript shape for the pricing catalog

scripts/
  generate_rate_card.py             # The script that produces the rate card

docs/
  06-seed-data.md                   # This file
```

The rate card is generated by `scripts/generate_rate_card.py`, which is
included so future refreshes are auditable - the user can tweak the base
rates and role multipliers and re-run the script to produce a consistent
new card.

The cloud pricing files are hand-curated because pricing tables don't
follow a simple multiplicative model (different SKUs, different units,
different pricing models). Phase 2 will replace these with live AWS
Pricing API and Azure Retail Prices API integrations behind the same
schema.

## Rate card methodology

The rate card is derived from three inputs:

### 1. Base rates per (level × geography)

Bill rates in USD/hour for a "generic" Software Engineer role at each
level × geography combination. These are mid-points of publicly available
Q1 2026 industry surveys (composite, not any single firm's quote):

| Level / Geography | US-On | LATAM-NS | India-Off |
|---|---:|---:|---:|
| Associate | $150 | $90 | $50 |
| Professional | $195 | $125 | $70 |
| Senior | $255 | $160 | $95 |
| Advisor | $325 | $205 | $130 |
| Principal | $400 | $255 | $170 |

(Full table covers 9 geographies in the generator script.)

### 2. Role multipliers

Each role scales relative to "Software Engineer = 1.00":
- Premium roles (Enterprise Architect 1.40, Security Architect 1.35,
  Engagement Lead 1.35) command higher rates.
- Standard engineering roles cluster around 1.00-1.10.
- Discounted roles (Support L1 = 0.55, Technical Writer = 0.75,
  QA Engineer = 0.75) reflect market realities.

### 3. Cost-to-bill ratio per geography

Internal cost rate as a fraction of bill rate. Lower in offshore (0.58)
than onshore (0.62-0.63) because absolute costs are lower so overhead
allocation differs.

### Spot checks

| Role | Level | Geography | Bill | Cost |
|---|---|---|---:|---:|
| Software Engineer | Senior | US-Onshore | $255 | $160 |
| Software Engineer | Senior | India-Offshore | $95 | $55 |
| Cloud Architect | Advisor | US-Onshore | $420 | $260 |
| Support L1 | Associate | Philippines-Offshore | $25 | $15 |
| Engagement Lead | Principal | US-Onshore | $540 | $335 |

All rates rounded to the nearest $5 - matches how real rate cards are
published.

### What's intentionally excluded

- **Level x role exclusions:** Support L1 has no Advisor or Principal
  variant; Engagement Lead has no Associate; pure-Architect roles start
  at Professional minimum. This avoids nonsensical entries.
- **Per-skill premiums:** A "Snowflake-certified Data Engineer" might
  warrant a 20% premium over generic Data Engineer; this isn't modeled
  because it would explode the catalog. Capture as a per-resource
  override on the rate.
- **Geography-specific roles:** A "JP-Onshore" or "DE-Onshore" with
  region-specific rates is not modeled - users add custom geographies
  via Settings as needed.

## Cloud pricing methodology

### Sourcing

Numbers are derived from publicly listed Q1 2026 prices for AWS us-east-1
and Azure eastus. They are list-price approximations, not negotiated
rates and not real-time.

### What's covered

| Category | AWS | Azure |
|---|---:|---:|
| Compute | 24 | 23 |
| Storage | 12 | 11 |
| Database | 19 | 15 |
| Networking | 16 | 14 |
| Security | 10 | 8 |
| Integration | 9 | 8 |
| Observability | 7 | 5 |
| Backup/DR | 3 | 3 |
| AI/ML | 11 | 9 |
| Other | 4 | 2 |
| **Total SKUs** | **115** | **98** |

Coverage is "common SKUs across the major service surface." Not every
SKU AWS offers (that would be thousands); enough that a typical
engagement can size cloud spend without inventing line items.

### Pricing model handling

Each SKU may appear multiple times with different `pricingModel` values
(OnDemand, Reserved1yr, Reserved3yr, etc.). The `unitCost` reflects the
ALREADY-DISCOUNTED rate for that pricing model - the engine does NOT
apply a discount multiplier on top.

This matters because cloud pricing data sources publish reserved and
on-demand as separate quotes, and applying a multiplier would
double-count. The `reservedDiscountReference` block at the top of each
file is informational only.

### Environment multipliers

Each pricing file includes:
```json
"environmentMultiplierDefaults": {
  "dev":     0.30,
  "test":    0.40,
  "staging": 0.60,
  "prod":    1.00,
  "dr":      0.45
}
```

When the user creates a cloud line item from the catalog, the planner
pre-fills `environmentMultiplier` based on the selected environment.
These defaults are firm-overridable in Settings > Preferences.

### What's intentionally excluded

- **Regional pricing variance.** AWS us-west-2 and ap-southeast-1
  have different prices than us-east-1. Phase 1 ships us-east-1 and
  eastus only; users adjust per line item if needed. Phase 2 ships
  multi-region pricing files.
- **Free tier / first-N-units pricing.** S3 prices are tiered (first
  50 TB at $23, next 450 TB at $22, etc.). Phase 1 uses the first-tier
  rate for all volumes. Real workloads above a few hundred TB need
  per-line-item overrides.
- **Commitment-based discounts beyond Reserved.** Enterprise Discount
  Programs, Private Pricing Agreements, Microsoft Enterprise Agreements
  - these are deal-specific and not modeled. Apply as a single discount
  percentage on the cloud subtotal if needed.

## Refresh strategy

### Today (Phase 1)
**Quarterly refresh, manual.** A version-controlled JSON file is the
source of truth. Bumping rates is a code review.

To refresh the rate card: edit `scripts/generate_rate_card.py`
(base rates, multipliers, exclusions) and re-run. The new JSON gets
checked in alongside the script.

To refresh cloud pricing: edit `seed/cloud-pricing/*.json` directly.
The diff in code review is the audit trail.

### Phase 2
**Live API integration.** A `PricingProvider` adapter interface
replaces the file reads. The adapter has implementations for:
- `LocalFilePricingProvider` (current behavior)
- `AwsPricingApiProvider` (AWS Pricing API)
- `AzureRetailPricesProvider` (Azure Retail Prices API)

The data model and the Cloud Planner UI are unchanged - only the
provider swaps. This is the seam in the architecture from #3.

## Versioning and rollback

Each seed file carries:
- `version` field (semver)
- `effectiveDate` (when the prices were valid)
- `isIllustrative: true` (always, until manually flipped)

When the user creates a project, the active rate card and pricing
catalog versions are snapshotted into the project's metadata. Later
refreshes to the catalogs don't retroactively affect existing
projects - the user can opt into a refresh per-resource or per-line-item.

This is critical for deal rooms: when someone asks "what rate card did
you use for this quote in March?", the answer is unambiguous.

## Adding new entries

### New role
1. Add the role name to `ROLE_CATALOG` in `src/types/resource.ts`.
2. Add a `ROLE_MULTIPLIERS` entry in the generator script.
3. Optionally add to `ROLE_LEVEL_EXCLUSIONS` if not all 5 levels apply.
4. Re-run the generator.

### New geography
1. Add the geo name to `Geography` in `src/types/resource.ts`.
2. Add a row to `BASE_BILL_RATES` for all 5 levels.
3. Add an entry to `COST_RATIO`.
4. Re-run the generator.

### New cloud SKU
Edit the relevant `aws-*.json` or `azure-*.json` file. Append an entry
following the existing pattern. Validate JSON parses (the project's CI
should do this in Phase 2).

### New cloud region
Copy an existing region file (`aws-us-east-1.json` →
`aws-eu-west-1.json`), adjust prices for the new region. AWS publishes
per-region price multipliers if needed as a starting point.

## Honesty notes

**1. These are NOT current prices.** They're illustrative midpoints from
a snapshot in time. Real engagements need real prices, either from your
rate card team or from the live cloud APIs (Phase 2).

**2. Real rate cards are usually narrower.** Most consulting firms don't
maintain 1,953 distinct entries - they have a tighter catalog of
~50-200 commonly-used combinations. The shipped card is wider so the
calculator handles edge-case staffing without complaining. Trim before
adopting.

**3. Real cloud catalogs are usually wider.** A live AWS Pricing API
response is tens of thousands of SKUs. Phase 1 ships the ones a typical
modernization actually uses. If your engagement uses, say, Outposts
or Local Zones, add those SKUs manually.

**4. The Medicaid-flavored seed scenario you held off on earlier could
slot in here.** If useful, I can produce a `seed/scenarios/medicaid-mmis-modernization.json`
that exercises the same data model but reflects state-Medicaid
realities (CMS phases, federal/state cost match, public-sector
procurement). Say the word.
